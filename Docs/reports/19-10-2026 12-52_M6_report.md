## Scope
M6: retry loop (exactly one), up to 3 claims per input with extractor, error states in UI, README.

## What was built
- **Retry loop** (`app/graph.py`): `summarize → route_after_summarize` (Unverifiable, or Mixed with <2 credible findings at ≥0.6) → `prep_retry` node (LLM rewrites the query via QUERY_REWRITE_PROMPT, increments `retries`, stores `search_query`) → back to `search`. Old findings are kept (`operator.add` reducer appends round 2).
- **State addition**: `search_query` key added to State (spec Section 6 has no slot for the refined query; noted as deviation).
- **Claim extractor** (`app/nodes.py` `extract_claims_llm`): single LLM call, up to 3 claims, passthrough for single short claims (and on LLM failure), notice text when input contains more claims. Runs in the API layer once per request; the graph runs once per claim (spec Section 4).
- **API** (`app/main.py`): per-claim loop with per-claim live progress/findings/result events, `notice` event, retries surfaced in results. Live-progress preserved via per-claim `astream` (I initially regressed this to `ainvoke` and fixed it).
- **UI** (`static/index.html`): multiple result cards (one per claim) with per-claim source tables, notice banner, error styling, retry count shown.
- **README.md** — setup under 10 lines.
- `tests/test_m6.py` — 4 offline tests: vague claim → exactly one retry (search called twice, `retries==1`, refined query set, verdict Unverifiable); strong evidence → no retry; extractor caps at 3 with notice; multi-claim SSE stream (3 results + notice + extractor progress).
